Lab guide 11

Identity, Access Management, and Automation

Provisioning accounts correctly, and using scripting to make the boring parts of security repeatable.

10-12 hours Week 10 complete
Before you start
  • secure-target VM up, sudo rights available

1. Provision an account with least privilege, then deprovision it cleanly

The full lifecycle, not just half of it — deprovisioning is where most real-world IAM failures actually happen.

Provision
sudo useradd -m -c 'Temp Contractor' tempcontractor
sudo passwd -l tempcontractor   # locked until they need it
sudo usermod -aG wheel tempcontractor 2>/dev/null || sudo usermod -aG sudo tempcontractor
Deprovision — cleanly, not just deleting the login
sudo pkill -u tempcontractor 2>/dev/null
sudo userdel -r tempcontractor
id tempcontractor 2>&1   # should now say 'no such user'

2. Account types, matched to purpose

User accounts for people. Privileged accounts (global or local scope) for elevated access — kept separate from a person's day-to-day account wherever possible. Service accounts run applications, not people. Third-party accounts belong to vendors needing limited access. Emergency access ("break glass") accounts exist for when normal auth is unavailable — tightly controlled and heavily logged specifically because they bypass normal controls.

3. Configure MFA on a sample service

Soft tokens are the most common real-world MFA method — this shows the mechanism.

Generate a TOTP secret and a matching code (the same math your phone's authenticator app does)
python3 -c "import secrets, base64; print(base64.b32encode(secrets.token_bytes(10)).decode())"
# That base32 string is what you'd scan as a QR code into an authenticator app in a real rollout

4. Access control models, compared

Role-based (RBAC): access tied to job role. Rule-based: access tied to explicit if-then rules (e.g. a firewall ACL). Time-based: access only during allowed hours. Mandatory (MAC): access decided by system-enforced labels, not the resource owner (this is what SELinux does). Discretionary (DAC): the resource owner decides who gets access (standard Linux file permissions). Just-in-time: privileged access granted only for the duration needed, then automatically revoked — the strongest defense against privilege creep.

5. Write a script that finds a common misconfiguration

Automation doing exactly what Week 9's manual checks did — but repeatably, on a schedule.

A short bash script checking for world-writable files
cat > ~/secplus-lab/check-perms.sh <<'EOF'
#!/bin/bash
found=$(find /etc -perm -002 -type f 2>/dev/null)
if [ -n "$found" ]; then
  echo "WARNING: world-writable files found in /etc:"
  echo "$found"
else
  echo "OK: no world-writable files in /etc"
fi
EOF
chmod +x ~/secplus-lab/check-perms.sh
~/secplus-lab/check-perms.sh

6. Guardrails and what automation can get wrong

Automation's whole value is consistency at scale — which is exactly why a mistake in the automation also happens at scale. Guardrails (approval steps, dry-run modes, blast-radius limits) exist to contain that. CompTIA also now includes AI capabilities here — agentic automation, chatbots, predictive analysis — as both an opportunity (faster response) and a risk (an AI agent with too much autonomy and too little guardrail is a new kind of insider-threat-shaped problem).
