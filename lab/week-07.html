Lab guide 7

Architecture Models and Zero Trust

How environments are actually built, and how Zero Trust changes the default assumption from "trusted network" to "prove it every time."

8-10 hours Week 6 complete
Before you start
  • secure-target and kali-tools VMs up

1. Cloud deployment models, compared honestly

Public cloud: shared infrastructure, lowest cost, least control. Private cloud: dedicated infrastructure, highest control, highest cost. Hybrid: a deliberate mix, usually to keep regulated data on-prem while bursting workload to public cloud. Community cloud: shared among organizations with common requirements (e.g. several government agencies). Serverless and multicloud are orthogonal choices layered on top of any of these. Infrastructure as Code (IaC) means your environment is defined in version-controlled files, not clicked together by hand — which makes it auditable and repeatable.

2. On-premises, air-gapped, and microservices

On-premises infrastructure trades cloud's elasticity for full physical control. An air-gapped network has no physical connection to any other network at all — the strongest isolation possible, common in OT and classified environments. Microservices break an application into small, independently deployable services — which shrinks each individual attack surface but multiplies the number of surfaces and the complexity of securing the connections between them.

3. Build an SSH tunnel between your two VMs

Secure communication over an otherwise plain connection — the same principle behind a VPN, at a smaller scale.

Tunnel a local port on kali-tools through to a service on secure-target
ssh -L 8443:localhost:22 shea@secure-target.lab -N &
ssh -p 8443 shea@localhost   # this now goes through the tunnel to secure-target's real SSH

4. Zero Trust architecture: three pillars

User authentication verified continuously, not once at login. Device management — checking device health (is it patched, does it have EDR running) and inventory (is this even a known device) before granting access. Application access control — access is scoped to the specific application/resource needed, not the whole network. Together these replace "you're on the VPN, so you're trusted" with "prove it, every request."

5. Design a least-privilege access policy

Concrete practice, not just definitions.

Give webops (from Week 1) exactly what it needs, verify it has nothing more
sudo -l -U webops
# Confirm: webops can restart sshd via sudo, and literally nothing else

6. Secure communication and identity management

Beyond VPN and tunneling: end-to-end encrypted messaging for sensitive comms, out-of-band management (a separate, isolated path to manage infrastructure that doesn't ride the same network it's protecting), and Security Service Edge (SSE), which centralizes secure access policy in the cloud rather than at a physical perimeter. On the identity side: Group Managed Service Accounts (gMSAs) automate credential rotation for service accounts, and watch for privilege creep — access that accumulates over a person's career and is never revoked as their role changes.

Check your work

Run these before you consider the lab finished.

  1. The SSH tunnel connects successfully on port 8443
  2. sudo -l -U webops still shows only the one allowed command
  3. You can explain the difference between hybrid and multicloud without hesitating
